# 2.1 Business Rules

Domain rules derived from the Prisma schema, the API services, and the frontend guards. Each rule references the code that enforces it.

## Identity and Plans

### 1. One user, one identity
A user is identified by `User.id` (Better Auth user id). Email is unique on `User`. Sign-up creates the user + initial session token.
_Source_: `prisma/schema.prisma` (`User`), `docs/career-hub-api/src/features/auth/`.

### 2. Plans are FREE / PRO / PREMIUM
- FREE is the default at sign-up.
- PRO and PREMIUM both unlock Scout features. There is currently no capability separating PREMIUM from PRO.
_Source_: `UserPlan` enum, `src/shared/config/plans.ts`.

### 3. Scout is a paid module
- Routes `/scout/*` and `/scout/playbooks` are guarded by `<PlanRoute allowedPlans={PRO_FEATURE_PLANS} />`.
- The hub sidebar hides Scout entries entirely for FREE users.
_Source_: `src/app/router/index.tsx`, `src/widgets/hub-layout/ui/HubSidebar.tsx`.

## Saves

### 4. A save is owned by one user
`Save.userId` is required. The API filters saves by `userId` and returns 404 (rather than 403) if a user requests a save they don't own — to avoid leaking existence.
_Source_: `docs/career-hub-api/src/features/saves/saves.service.ts` (`getSaveById`).

### 5. A save always has exactly one current club stint
Created together with the save; `ClubStint.isCurrent = true` for exactly one row per save at any moment. Changing club closes the previous stint (`endYear`, `isCurrent = false`) atomically.
_Source_: `prisma/schema.prisma` (`ClubStint`), club-stints service.

### 6. A save has a current season string
Format `"YYYY/YY"` (e.g., `2026/27`). Advancing `currentSeason` via `PATCH /saves/:id` cascades server-side to create new `TeamSeasonStats`, `PlayerSeasonStats`, and trophy placeholders.
_Source_: `saves.routes.ts` PATCH description.

### 7. Deleting a save deletes everything under it
`onDelete: Cascade` on every child relation (`ClubStint`, `Player`, `Transfer`, `ScoutPlaybook`, `ShortlistItem`, `SavedSearch`, ...). No soft delete.

## Squad

### 8. A player belongs to one save
`Player.saveId` is required; cascaded on save delete.

### 9. A player is "active" iff `activeClubStintId` is non-null
Released or loaned-out players have `activeClubStintId = null` (or point at a non-current stint).
_Source_: `Player.activeClubStintId`, `usePlayers(saveId, active)`.

### 10. Shirt numbers are unique within an active squad
Server returns 409 `SHIRT_NUMBER_CONFLICT` with a human-readable message when a duplicate is attempted.
_Source_: `client.ts` `extractErrorMessage` special-case; surfaced in `PlayerModal`.

### 11. Positions are a fixed enum
`GOL`, `ZAG`, `MEI`, `ATA`, `LD`, `LE`, `VOL`, `MC`, `ME`, `MD`, `PE`, `PD`, `SA`. Primary in `position`; alternates in `alternativePosition.positions[]`.

### 12. Player status drives squad UX
`Crucial`, `Important`, `Role`, `Sporadic`, `Promising`, `Loan`. `Loan` indicates the player is currently on loan (in or out). Other status values reflect tactical importance.

### 13. Salary is in thousands; money figures are in millions
- `Player.salary` — thousands of € (75 = €75K).
- `Player.marketValue`, `Save.budget`, `Save.balance`, `Transfer.fee` — millions of € (100 = €100M).
_Source_: API `CLAUDE.md`, mirrored helpers in `src/shared/lib/currency.ts`.

### 14. OVR is bounded to 1–99
Validated client-side in `PlayerModal`; the API also clamps.

## Transfers

### 15. Transfer types are fixed
`compra`, `venda`, `emprestimo_entrada`, `emprestimo_saida`.

### 16. Creating a transfer affects the save's balance
The API performs the financial mutation transactionally and returns the updated `save` in the response payload.
_Source_: `transfers.service.ts`, observed in client `transfersApi.create` return type.

### 17. Incoming transfers may auto-create a player
For `compra` and `emprestimo_entrada`, the API may create a new `Player` row when `playerId` is not provided. The created id is returned in the response.

### 18. Outgoing transfers update the linked player
For `venda` and `emprestimo_saida`, the player's `activeClubStintId` is detached or updated; loan state is reflected in the player record.

## Stats and Trophies

### 19. Stats rows are auto-created
- On save creation: one `TeamSeasonStats` per competition of the club's country.
- On season advance: new `TeamSeasonStats` per competition + `PlayerSeasonStats` per active player.

### 20. Trophies are unique per (stint, competition, year)
Enforced by `@@unique([clubStintId, competitionId, year])`. A given competition can be lifted at most once per stint per year.

### 21. Cup results are a fixed enum
`Campeao`, `Final`, `Semifinal`, `Quartas`, `OitavasOuFaseDeGrupos`, `Eliminado`, `NaoParticipou`.

### 22. League position is meaningful only for leagues
Other competition types should not show a "league position" field in the UI.

## Scout

### 23. The FC26 dataset is read-only
`Fc26Player` rows are seeded server-side; the frontend never mutates them. Users only attach them via `ShortlistItem` records.

### 24. Shortlist items are unique per (save, fc26Player)
`@@unique([saveId, fc26PlayerId])`. A player can be shortlisted only once per save.

### 25. Saved searches are scoped to a save
`@@unique([saveId, name])`. A user cannot reuse the same query name within one save.

### 26. Playbooks are scoped to a save
`@@unique([saveId, name])`. Exactly one playbook per save can have `isDefault = true` (enforced via the `@@index([saveId, isDefault])` plus service logic that flips the flag).

### 27. Fit-score requires squad context
When `useFc26Players` is called inside the Scout module, `saveId` is included and an `objective` (defaulting to `"balanced"`) is set so the API can compute `fitScore`, `fitConfidence`, and `fitProfileSize` against the current squad.

## Chat (Mister)

### 28. The chat is per-user, client-stored
Conversation history lives in `localStorage["junior-chat:<userId>"]` and `["junior-chat-history:<userId>"]`. Capped at 20 conversations.

### 29. The chat sees only the user's own data
The MCP server is mounted with the user's bearer token; tool calls operate strictly under that authenticated context. There is no cross-tenant data path.

### 30. The chat uses OpenAI Responses API with MCP
The API forwards messages to OpenAI Responses with the MCP server (`/mcp`) registered as a tool source. `previousResponseId` chains turns.

## Governance

### 31. All non-auth API calls require a session
Bearer-token validated by `requireAuth()` server-side; the entire frontend hub is wrapped in `<ProtectedRoute />`.

### 32. 401 from the API means immediate sign-out
The frontend's `unauthorizedHandler` (registered by `AuthProvider`) clears the session on any 401 outside `/auth/sign-*`. There is no per-call recovery — the global behavior is intentional.

### 33. Better Auth rate-limits apply server-side
Surfaced to the client via 429 + `Retry-After` header; captured on `ApiError.retryAfter`. Auth endpoints have their own rate-limit policy.
