## Itens

### M-01. UI/UX do fluxo "Avançar temporada" e modais subsequentes — - [ ]
- **Resp.**: Frontend.
- **Estado atual**: [NewSeasonModal](../../src/features/new-season/ui/NewSeasonModal.tsx) e os modais subsequentes não receberam a revisão de UI/UX já aplicada às demais telas.
- **Melhoria**: alinhar ao design system e ao padrão visual do restante.
- **Tipo**: UX.
- **Done when**: o fluxo está consistente com as telas já revisadas.

### M-02. UI do campinho e da sala de troféus — - [ ]
- **Resp.**: Frontend.
- **Estado atual**: [FieldScreen](../../src/features/field/ui/FieldScreen.tsx) e a sala de troféus pedem refino visual.
- **Melhoria**: ajustes de UI nas duas telas.
- **Tipo**: UX.

### M-03. Revisão completa de responsividade — - [ ]
- **Resp.**: Frontend.
- **Estado atual**: layout pensado para desktop.
- **Melhoria**: revisar todas as telas para toque e telas menores.
- **Tipo**: UX · acessibilidade.
- _Liga: Roadmap Horizonte 3 (mobile-first)._

### M-04. Records em History: mostrar mais de cara — - [ ]
- **Resp.**: Frontend (API só se faltar dado).
- **Estado atual**: cada record exibe só o 1º colocado do ranking.
- **Melhoria**: exibir mais posições diretamente na tela.
- **Tipo**: UX · densidade de informação.

### M-05. History: clubes pelos quais o jogador do ranking atuou com você — - [ ]
- **Resp.**: Ambos — exibição (FE) + agregação por jogador/clube (API), _a confirmar_.
- **Estado atual**: o ranking não mostra por quais dos seus clubes o jogador passou.
- **Melhoria**: anexar à entrada do ranking os clubes sob a sua gestão em que o jogador atuou.
- **Tipo**: UX.

### M-06. Persona do chatbot — - [ ]
- **Resp.**: API (prompt/persona server-side / MCP); FE em affordances pontuais.
- **Estado atual**: a persona do assistente precisa melhorar bastante.
- **Melhoria**: redefinir tom, conhecimento e limites do assistente.
- **Tipo**: UX · qualidade do produto.
- _Liga: [F-03](4.2_Features.md) (histórico de chat)._

### M-07. Reestruturação funcional da aba Scout — - [ ]
- **Resp.**: Ambos — fluxos/UI (FE) + decidir scoring server vs client (API). **Precisa discovery.**
- **Estado atual**: funciona, mas não bem; `scoutingApi` existe na API e está **sem uso** no FE ([ScoutScreen](../../src/features/scout/ui/ScoutScreen.tsx) usa lógica client-side). Saved queries e shortlist já persistem no servidor ([M-09](4.3_Improvements.md) concluído).
- **Melhoria**: rediscutir as funcionalidades e reestruturar a aba (escopo a definir antes de estimar).
- **Tipo**: UX · código.
- _Liga: [M-09](4.3_Improvements.md), [M-06](4.3_Improvements.md)._

### M-08. Custo/arquivamento de jogadores históricos por save — - [ ]
- **Resp.**: API / infra.
- **Estado atual**: cada save acumula muitos jogadores; preocupação de inchaço e custo do banco com dados de temporadas passadas.
- **Melhoria**: estratégia de retenção/arquivamento que **mantém o histórico** sem onerar o banco quente.
- **Tipo**: performance · custo · infra.
- _Liga: [F-05](4.2_Features.md) (depende do histórico retido)._

### M-09. Persistência server-side de saved queries e shortlist — - [x]
- **Resp.**: Frontend (migração) — os clients de API já existem.
- **Estado atual**: ambos vivem em `localStorage` ([ScoutScreen](../../src/features/scout/ui/ScoutScreen.tsx)); `shortlistApi` e `savedSearchesApi` já existem no client porém **sem uso**.
- **Melhoria**: migrar para o servidor (persistência e roaming entre dispositivos).
- **Tipo**: DX · UX (continuidade de dados).
- _Carried-over: Fase 3 do roadmap de débito (clients criados, UI não migrada)._
- _Entregue_: hooks [`useShortlist`](../../src/features/scout/model/useShortlist.ts) e [`useSavedSearches`](../../src/features/scout/model/useSavedSearches.ts); o `ScoutScreen` deriva shortlist e saved queries do servidor (sem `localStorage`). Conteúdo antigo do `localStorage` **não** foi migrado, por decisão. A saved search persiste só `name`+`filters`; como o dataset FC26 é read-only (regra 23), os resultados do detalhe são re-buscados ao vivo pelos filtros._
