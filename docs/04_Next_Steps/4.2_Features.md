# 4.2 Features

Capacidade **nova** que o produto ainda não oferece. Uma feature adiciona superfície — uma tela, um fluxo, uma integração. Refinar algo que já existe é [4.3 Melhoria](4.3_Improvements.md); consertar algo que existe e está errado é [4.1 Correção](4.1_Corrections.md).

> Se a feature depende de mudar uma regra do domínio, registre também o item correspondente em [4.4 Alterações de Regra de Negócio](4.4_Business_Rule_Changes.md) e referencie-o aqui.

**Status:** `- [ ]` não iniciado · `- [~]` em andamento · `- [x]` concluído.

### F-01. Competições no save — - [ ]
- **Resp.**: Ambos — modelo/endpoints (API) + seleção e vínculo na UI (FE).
- **Estado atual**: já há suporte a clubes e ligas; a API expõe `competitionsApi` (`/competitions`, `/competitions/european`) e o FE já consome em [useCompetitions](../../src/features/change-club/model/useCompetitions.ts) (fluxo change-club). Falta modelar competições no save propriamente dito.
- **Proposta**: registrar/seguir competições (liga, copas nacionais, supercopa, copas europeias) e vinculá-las a temporadas, troféus e estatísticas.
- **Depende de**: definição de profundidade (só troféus? tabela? artilharia?).
- **Done when**: usuário associa competições às temporadas e elas aparecem onde fizer sentido.
- _Origem: lista de próximos passos. Liga: [F-05](4.2_Features.md), troféus e stats._

### F-02. "Chamar de volta" jogador emprestado (recall) — - [x]
- **Resp.**: Ambos — ação/modal (FE) + reverter o empréstimo e religar ao elenco (API).
- **Problema do usuário**: hoje não há como encerrar o empréstimo antes da virada de temporada.
- **Proposta**: ação de recall que retorna o jogador ao elenco fora da troca de temporada.
- **Done when**: recall disponível e o jogador volta ao elenco com estado correto.
- _Origem: cluster Empréstimos. Liga: [R-02](4.4_Business_Rule_Changes.md), [C-01](4.1_Corrections.md)._

### F-03. Histórico de chat persistido em banco — - [x]
- **Resp.**: Ambos — persistir + endpoint de leitura (API) + reidratar do servidor (FE).
- **Estado atual**: o chat só guarda histórico em `localStorage` ([useJuniorChat](../../src/features/scout/model/useJuniorChat.ts)); o servidor apenas encadeia via `previousResponseId`, sem endpoint de histórico. Não há persistência server-side nem roaming entre dispositivos.
- **Proposta**: persistir conversas por usuário/save e reidratar a partir do servidor.
- **Done when**: o histórico sobrevive a outro dispositivo/sessão.
- _Carried-over: Roadmap Horizonte 3. Liga: [M-06](4.3_Improvements.md) (persona)._
- _Entregue_: a API agora persiste o histórico no banco. O FE deixou de usar `localStorage`: [`chatApi`](../../src/shared/api/modules/chat.ts) ganhou `listConversations`/`createConversation`/`listMessages`/`deleteConversation` e `sendMessage` passa `conversationId`; o hook [`useJuniorChat`](../../src/features/scout/model/useJuniorChat.ts) é a fonte da verdade server-side (lista por `saveId`, cria a conversa na 1ª mensagem com título derivado, reidrata ao trocar de conversa, trata `429`/`Retry-After`, `404` limpando a seleção). CSRF/cookie/credentials já são tratados pela camada [`http`](../../src/shared/api/http.ts) e `/chat` já estava marcado como rota PRO._
