# 3.6.1 Auth

## Responsibility

Owns the user session lifecycle: sign-up, sign-in, sign-out, session hydration from storage, and global 401 handling. All other features depend on `useAuth()` to know who the current user is.

## Internal Architecture

```
features/auth/
├── api/                                  (empty — uses shared/api/client.ts directly)
├── lib/
│   └── auth-storage.ts                   localStorage helpers (token, user, active-save)
├── model/
│   ├── AuthContext.tsx                   <AuthProvider> + session orchestration
│   ├── auth-context-core.ts              context object + AuthContextValue type
│   └── useAuth.ts                        public hook
└── ui/
    ├── AuthGuards.tsx                    <ProtectedRoute>, <PublicOnlyRoute>, <PlanRoute>

```

## Dependencies

- [`shared/api/client.ts`](../../../src/shared/api/client.ts) — `authApi`, `registerUnauthorizedHandler`, `setCsrfToken`/`clearCsrfToken`, `ApiUser`, `ApiSession`.
- `@tanstack/react-query` — clears the cache on sign-out.
- `react-router-dom` — guards redirect via `<Navigate />`.
- `localStorage` — keys: `session_user`, `active-save-id:<userId>`. **The session token is no longer in localStorage** — it lives in an httpOnly cookie set by the API; the CSRF token is kept in memory. `purgeLegacySessionToken()` removes any leftover pre-cutover `session_token`.

## Data Flow

### Bootstrap
1. `AuthProvider` mounts inside `Providers`.
2. `hydrateSession()` purges any legacy token, then reads the cached `session_user`; if missing, `isLoading = false` and the user stays unauthenticated (a bare session cookie with no cached user is re-established on the next explicit sign-in).
3. If present: optimistically rehydrate `user` from `localStorage["session_user"]`, then call `authApi.getSession()` to validate the cookie session.
4. On success (a body with a `user`) → `setUser/setSession`.
5. On failure → `clearSession()` → empties localStorage, resets state, calls `queryClient.clear()`. **"Failure" = any response without a `user`**: a thrown error (401), a `null` body, or an empty `{}` body. The guard checks `currentSession?.user` (not mere truthiness) so it is robust to all three. _The boot-time refresh-logout bug is resolved: `GET /auth/session` now injects the cookie token as Bearer (mirroring `requireAuth`) and normalizes the unauthenticated case to `401`/`null`, so a logged-in user survives a reload._

### Sign-in / Sign-up
1. `authApi.signIn` or `authApi.signUp` returns `{ csrfToken, user }`; the API also sets the session as an httpOnly cookie (the session token is no longer in the response body — the cookie is the source of truth).
2. The `csrfToken` is stored in memory via `setCsrfToken` (echoed back as `X-CSRF-Token` on writes, double-submit).
3. A follow-up `authApi.getSession()` is called to populate the `session` object (best-effort; failure is swallowed).

### Sign-out
1. `authApi.signOut()` is invoked (failure tolerated).
2. `clearSession()` runs regardless — local state is the source of truth for "signed out".

### Global 401 handler
- `shared/api/client.ts` exposes `registerUnauthorizedHandler(fn)`.
- `AuthProvider` registers `clearSession` on mount, unregisters on unmount.
- Any HTTP 401 on a non-`/auth/sign-*` path triggers `clearSession` → user lands on `/login` on next protected-route render.

## Guards

| Guard | Behavior |
|---|---|
| `ProtectedRoute` | Loader while hydrating → if not authenticated, redirect to `/login` with `state.from` (expired session is "sign in again", not "forbidden"; `/unauthorized` is reserved for true 403-style dead-ends). |
| `PublicOnlyRoute` | Loader while hydrating → if authenticated, redirect to `state.from ?? /app` (so the login round-trip returns to the originally requested route). |
| `PlanRoute` | Loader while hydrating → if `user.plan` not in `allowedPlans`, redirect to `/pricing`. Forwards outlet context. |

## Local Domain Rules

1. The cached user object and the active-save id are the only authentication-related items in localStorage; the session token is an httpOnly cookie owned by the API, not readable by JS.
2. Sign-out clears the cached user, the in-memory CSRF token, and the active-save id (the active-save id is cleared even if `authApi.signOut` fails); the cookie is cleared server-side by `authApi.signOut`.
3. A successful 401 on `/auth/sign-in` or `/auth/sign-up` does **not** clear the session — these endpoints intentionally return 401 for bad credentials and must not nuke an existing session.

## Extension Points

- Add `useRequireAuth(role)` for granular role checks if `ApiUser.role` ever splits beyond `ADMIN | USER`.
- Add a refresh-token path if Better Auth gains rotating tokens.
- Add OAuth providers via `authApi` (Better Auth supports them server-side).
