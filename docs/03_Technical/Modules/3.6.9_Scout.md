# 3.6.9 Scout

## Responsibility

Paid-only (PRO/PREMIUM) module that helps users find signings:

- **AI Assistant ("AIssistent Coach" / "Mister")** — chat with an LLM that has tool-access to the user's save via MCP.
- **Filters** — query the FC26 dataset (15k+ real players) by attributes, position, league, traits, plus a fit-score relative to the current squad.
- **Saved Queries** — persisted filter sets per save.
- **Shortlist** — pinned FC26 players for the user to track.

## Internal Architecture

```
features/scout/
├── model/
│   ├── currentClubFilter.ts              helper to exclude players already at user's club
│   ├── useFc26Players.ts                 useFc26Players, useFc26Player, useFc26PlayerFilters
│   └── useJuniorChat.ts                  chat state + localStorage history (per user)
├── ui/
│   └── ScoutScreen.tsx                   single screen with internal sections (ai/filters/shortlist/archive)
└── index.ts
```

`ScoutScreen` accepts a `section` prop (`"ai" | "filters" | "shortlist" | "archive"`) and is mounted four times in the router with different sections — the URL changes (`/scout/ia`, `/scout/filtros`, `/scout/shortlist`, `/scout/consultas`) but the component is one.

## Data Flow

### Filters
1. `useFc26PlayerFilters()` provides metadata (positions, nations, leagues, clubsByLeague). Cached 24h client-side.
2. User builds a filter object — numeric ranges (`min*`/`max*`), position lists, traits, sort, pagination, optional `objective` (`balanced | title | youth | rebuild`).
3. `useFc26Players(filters, saveId)` calls `/fc26-players` with the save id included. The server uses it to compute `fitScore`, `fitConfidence`, `fitProfileSize`.
4. Pagination handled via `limit` (max 100) and `offset`. Placeholder data keeps the previous page visible during refetch.

### AI chat (Mister)
1. `useJuniorChat` reads/writes two localStorage entries per user: the current conversation and a capped history (`MAX_HISTORY = 20`).
2. `chatApi.sendMessage({ message, previousResponseId })` → server uses OpenAI Responses API with the MCP server (`/mcp`) as a tool source, authenticated with the user's bearer token.
3. Server returns `{ reply, responseId }`. The id is stored to chain subsequent calls.
4. Errors → `toast.error(extractErrorMessage(err))`.

### Shortlist and Saved Queries
- The API has dedicated routes (`/shortlist`, `/saved-searches`), but they are **not yet exposed in `shared/api/client.ts`**. Section UIs read/write through helpers internal to `ScoutScreen` or via the MCP chat indirectly. See [3.5 Technical Debt](../3.5_Technical_Debt.md#3-some-api-features-lack-frontend-client-wrappers).

## Local Domain Rules

1. The whole module is plan-gated: `<PlanRoute allowedPlans={PRO_FEATURE_PLANS} />` in the router.
2. The sidebar hides Scout items entirely for FREE users (`canAccessProFeature(plan)`).
3. Chat history is stored client-side only — never sent to the API, never synced across devices.
4. The fit score is computed server-side from the current squad's profile against the candidate; `fitConfidence` reflects how much squad data was available (high/medium/low/none).
5. The fit-score `objective` defaults to `"balanced"` when not provided.
