# 3.6.4 Field Lineup

## Responsibility

Lets the user arrange the active squad onto a pitch with a chosen formation. This is a visual planning surface, not a tactical engine — it does not run matches or compute simulation outcomes.

## Internal Architecture

```
features/field/
├── ui/
│   └── FieldScreen.tsx                   pitch layout + drag-drop slots + formation picker
└── index.ts
```

No `model/` folder — the screen consumes `usePlayers` from `features/squad/model` directly and keeps formation state local. There is no API persistence of the lineup (yet).

## Dependencies

- [`features/squad/model/usePlayers`](../../../src/features/squad/model/usePlayers.ts) — roster source.
- [`shared/lib/playerPositions.ts`](../../../src/shared/lib/playerPositions.ts) — position labels.
- `@dnd-kit/core` — drag-and-drop. (Listed in `package.json`; used by this screen.)
- `lucide-react` — `Shirt` icon, pitch markers.

## Data Flow

1. `FieldScreen` reads `usePlayers(saveId, active=true)`.
2. The user picks a formation (`4-3-3`, `4-4-2`, `4-2-3-1`, …) — formation shape determines slot positions.
3. Players are dragged from the bench into slots. Slot ↔ player mapping is held in component state (`useState`/`useReducer`).
4. State is **not persisted** to the API — refreshing the page resets the board.

## Local Domain Rules

1. Only `active` players (those with a non-null `activeClubStintId`) appear on the bench.
2. A slot enforces a positional family (e.g., a CB slot accepts `ZAG`); secondary positions (`alternativePosition.positions[]`) qualify a player for adjacent slots.
3. The screen is purely client-side — there is no server-side validation of the formation.

## Extension Points

- Persist the lineup per save (would require a new API endpoint, e.g. `PATCH /saves/:id/lineup`).
- Multiple saved formations per save (starting XI, B-team, set pieces).
- Auto-fill best XI by OVR within positional constraints.
- Compare two lineups side-by-side.
- Surface average OVR / chemistry score for the chosen XI.
