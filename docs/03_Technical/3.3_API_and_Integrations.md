# 3.3 API and Integrations

## Overview

The frontend talks to a single backend: **fc26-career-hub-api** (Fastify + Prisma + Postgres + Redis), mirrored under [`docs/career-hub-api/`](../career-hub-api/) for reference. The HTTP surface is fully captured by the typed objects under `src/shared/api/` — a shared `http.ts` core plus one `modules/<domain>.ts` per resource, all re-exported through the [`client.ts`](../../src/shared/api/client.ts) barrel (the canonical import path).

Production OpenAPI docs (Swagger UI) are served by the API at `<api-base>/docs`. Use them as the live source of truth for request/response shapes when in doubt.

## Transport

### Base URL
Resolved in `shared/api/http.ts` (`resolveBaseUrl`):

1. `import.meta.env.VITE_API_URL` if set — accepts a relative same-origin path (`/api`, the default) **or** an absolute URL (the cross-site escape hatch).
2. Else, same-origin `/api` in the browser; under the test runner, the absolute Railway host (relative URLs have no base to resolve against in jsdom).
3. `/api` is appended if missing.

### Same-origin proxy (Safari ITP)
The SPA and the API live on different registrable domains, which made the httpOnly session cookie **cross-site** — Safari's ITP and tightening third-party-cookie rules cap or drop it, silently ending sessions. To fix this, all browser traffic is routed through the app's **own origin** so the cookie stays **first-party**:

- **Production** — a Vercel rewrite ([`vercel.json`](../../vercel.json)) proxies `/api/:path*` to the backend.
- **Development** — the Vite dev proxy ([`vite.config.ts`](../../vite.config.ts)) forwards `/api` to `DEV_API_PROXY_TARGET` (with `cookieDomainRewrite` so the cookie binds to localhost).

Because the cookie is `SameSite=Lax`, **every browser call must go through `/api`** — a direct cross-site call to the backend would carry no cookie (401). The backend host was dropped from the CSP `connect-src` (now `'self'` + the font hosts) to enforce this. Bearer/MCP/mobile clients are unaffected (they don't use the cookie).

### Headers & credentials
- `Content-Type: application/json`.
- Every request is sent with `credentials: "include"` so the httpOnly session cookie rides along (no `Authorization` header from the browser).
- On mutating methods, a double-submit `X-CSRF-Token` header is added from the in-memory CSRF token (lazily fetched via `GET /auth/csrf` when absent). `/auth/sign-in` and `/auth/sign-up` are CSRF-exempt.

### Status handling
- `204` → resolves with `undefined`.
- `401` (on any path other than `/auth/sign-in`, `/auth/sign-up`) → calls `unauthorizedHandler()` which clears the session.
- `429` → captures `Retry-After` header into `ApiError.retryAfter`.
- Other non-OK → throws `ApiError`.

### Error contract
Backend responses on failure follow one of two shapes:

```json
{ "error": "Erro interno do servidor.", "statusCode": 500 }
{ "error": "SHIRT_NUMBER_CONFLICT", "message": "Camisa 10 já está em uso", "statusCode": 409 }
```

The frontend `ApiError` carries `{ message, status, data, isNetworkError, retryAfter }`. Use `extractErrorMessage(err)` from `shared/api/client.ts` to compute the user-facing string — it knows about specific codes like `SHIRT_NUMBER_CONFLICT`.

## Endpoints

All endpoints below are prefixed with `/api`. Auth endpoints are public; everything else requires a valid session token.

### Auth — `authApi`
| Method | Path | Notes |
|---|---|---|
| `POST` | `/auth/sign-up/email` | Body `{ name, email, password, plan? }`. Returns `{ csrfToken, user }`; sets the session cookie. |
| `POST` | `/auth/sign-in/email` | Body `{ email, password }`. Returns `{ csrfToken, user }`; sets the session cookie. |
| `GET` | `/auth/session` | Returns `{ session, user } \| null` (401 → `null`). |
| `GET` | `/auth/csrf` | Returns `{ csrfToken }`. Used to lazily re-seed the in-memory CSRF token after a reload. |
| `POST` | `/auth/sign-out` | Returns `{ success: true }`; clears the session cookie. |

Better Auth is the underlying provider (in bearer mode); a custom serializer wraps the returned token into the httpOnly `session_token` cookie and emits the `csrf_token` cookie. The cookie is **host-only** (no `Domain` attribute — required because the Vercel rewrite forwards `Set-Cookie` verbatim) and `Secure; SameSite=Lax`. The SPA never reads `session_token`. Writes are protected by the double-submit CSRF token (returned on sign-in/up, re-seeded via `GET /auth/csrf`) — kept as defense-in-depth since `SameSite=Lax` alone doesn't cover all writes. The API's `trustedOrigins` allowlist must include every frontend origin (production + each Vercel preview + `http://localhost:8080`); wildcards are disallowed by design.

## MCP Integration

The API mounts an MCP (Model Context Protocol) server at `/mcp` (see `docs/career-hub-api/src/mcp/`). It exposes career data as tools (squad, transfers, stats, trophies) consumable by the OpenAI Responses API.

- The chat endpoint sets up the MCP tool with the user's session token forwarded as `Authorization: Bearer`.
- `require_approval: 'never'` — tool calls run without confirmation, since they are read-only for the authenticated user's own data.
- The frontend never talks to `/mcp` directly. It only calls `/chat/messages`.

## Auth Storage

The session token itself is **not** in localStorage — it's an httpOnly cookie set by the API. `AuthProvider` ([`src/features/auth/model/AuthContext.tsx`](../../src/features/auth/model/AuthContext.tsx)) only caches non-secret hydration state in localStorage:
- `session_user` — cached `ApiUser` JSON (used to render UI immediately while `getSession` validates the cookie in background).
- `active-save-id:<userId>` — last-selected save id (cleared on sign-out).
- The CSRF token is held **in memory** (not persisted); `purgeLegacySessionToken()` strips any pre-cutover `session_token` left over from before the cookie migration.

Helpers in [`src/features/auth/lib/auth-storage.ts`](../../src/features/auth/lib/auth-storage.ts) own all reads/writes. Never touch `localStorage` for auth state from elsewhere.

## Environment Variables (frontend)

| Variable | Purpose |
|---|---|
| `VITE_API_URL` | API base URL. Defaults to the same-origin path `/api`; an absolute URL bypasses the proxy (cross-site). |
| `DEV_API_PROXY_TARGET` | Backend the Vite dev proxy forwards `/api` to. Build-time only (not a `VITE_*` var); defaults to the Railway host. |

Only `VITE_*` names are exposed to the client. The former `NEXT_PUBLIC_API_URL` fallback and the hardcoded Vercel default were removed; see [`.env.example`](../../.env.example).

## Rate Limits

- The API uses Better Auth's rate limiter and per-endpoint limits.
- 429 responses include `Retry-After` (seconds). The client surfaces this on `ApiError.retryAfter`.
- For load testing, the API supports `DISABLE_RATE_LIMIT=true` env var server-side. Never set this in real production traffic.

## Caching (backend, but relevant to frontend behavior)

The API caches list and detail endpoints in Redis with per-service TTLs. The frontend's React Query cache sits on top:
- **`staleTime` is aligned with the API's Redis TTLs** via the single `CACHE_TTL` map in [`src/shared/api/cache-ttl.ts`](../../src/shared/api/cache-ttl.ts), mirrored value-by-value from the API's per-service TTL constants (`API/career-hub-api/src/features/<feature>/<feature>.service.ts`). Without this the client would refetch on every mount/focus only to receive the value the API is still serving from Redis. Current alignment:

  | Resource (query key) | API Redis TTL | Client `staleTime` |
  |---|---|---|
  | saves list (`["saves"]`) | 15min | 15min |
  | save detail (`["saves", id]`) | 30min | 30min |
  | players list (`["players", …]`) | 1h (30min for active/loaned) | same split |
  | player detail (`["players", id, pid]`) | 1h | 1h |
  | transfers (`["transfers", …]`) | 30min | 30min |
  | team stats (`["teamStats", …]`) | 1h | 1h |
  | trophies (`["trophies", …]`) | 1h | 1h |
  | club stints (`["clubStints", …]`) | 1h | 1h |
  | competitions | 24h | 24h |
  | clubs | _in-memory constant, no Redis_ | 24h (static) |
  | fc26 players (list/detail/filters) | 24h | 24h |
  | snapshots, audit log, playbooks, deleted saves | _not cached_ | 0 (always revalidate) |

- The API invalidates its Redis cache on writes; the frontend invalidates its query keys in each mutation's `onSuccess`. The frontend invalidates by **key prefix**, so `["players", saveId]` busts the detail and parametrised-list keys too. Every write invalidates a superset of what the API busts, so an explicit invalidation always wins over `staleTime`.
- If you see stale data, check both layers.
