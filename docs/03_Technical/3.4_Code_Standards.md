# 3.4 Code Standards

## Base

- TypeScript (strict), React 18 function components with hooks.
- ESLint via [`eslint.config.js`](../../eslint.config.js) (flat config) — base + TS + react-hooks + react-refresh.
- Vitest for unit/component, Playwright for E2E.
- Path alias `@/` → `src/` (see [`tsconfig.json`](../../tsconfig.json) and [`vite.config.ts`](../../vite.config.ts)). Always import via `@/...`; never via deep relative paths.

## Folder Conventions

### FSD layers
See [3.1 Architecture](3.1_Architecture.md) — `app → pages → widgets → features → entities → shared`. Lower layers must not import from higher ones.

### Inside a feature
```
features/<name>/
├── api/        # (optional) endpoint wrappers when shared/api/client.ts isn't enough
├── model/      # hooks (useX), context, pure logic, derived types
├── lib/        # helpers
├── ui/         # components
└── index.ts    # barrel — single public surface for other layers
```

Other layers import the feature **only via `index.ts`**. Reaching into `features/X/ui/Foo` from outside is forbidden.

### Inside `shared/`
- `api/client.ts` — single HTTP client + typed API objects + types. Append new sections at the bottom, grouped by domain with the `// ─── X ───` divider style.
- `lib/` — pure helpers, no React.
- `ui/` — shadcn primitives. Customize in place; do not fork.

## Naming

- **Components**: PascalCase. One per file. Filename matches component (`SquadScreen.tsx`).
- **Hooks**: `use` prefix, camelCase (`useSaves`, `usePlayer`).
- **Types/interfaces**: PascalCase. API types start with `Api` (`ApiSave`, `ApiPlayer`). Domain enums use the API casing exactly (`Position`, `PlayerStatus`).
- **Files in `shared/lib/`**: camelCase (`playerPositions.ts`, `playerTransferStatus.ts`).
- **Files in `shared/ui/`**: kebab-case (matches shadcn convention: `alert-dialog.tsx`, `dropdown-menu.tsx`).

## Type Strategy

- API response types live in [`src/shared/api/client.ts`](../../src/shared/api/client.ts) as `ApiX` interfaces. They are the canonical contract.
- Feature-local types live next to the consumer in `features/<name>/model/`.
- Domain entity types live in `entities/<name>/model/`.
- Avoid `any`. Where unavoidable (e.g., third-party SDKs without types), confine to one line with an `eslint-disable-next-line` comment if needed.

## React Query Pattern

```ts
// features/<name>/model/useX.ts
import { useQuery, useMutation, useQueryClient } from "@tanstack/react-query";
import { xApi } from "@/shared/api/client";

export function useX(id: string | null) {
  return useQuery({
    queryKey: ["x", id],
    queryFn: () => xApi.get(id!),
    enabled: !!id,
  });
}

export function useUpdateX() {
  const qc = useQueryClient();
  return useMutation({
    mutationFn: ({ id, data }: { id: string; data: ... }) => xApi.update(id, data),
    onSuccess: (_res, vars) => qc.invalidateQueries({ queryKey: ["x", vars.id] }),
  });
}
```

### Query-key conventions
- First element is the resource name.
- Subsequent elements are id-like inputs in order of specificity: `["players", saveId, active, season, loaned]`.
- Cross-domain invalidations on save updates: `["saves"]`, `["saves", id]`, `["teamStats", id]`, `["players", id]`, `["trophies", id]` (see [`useSaves.ts`](../../src/features/saves/model/useSaves.ts) for the canonical pattern).

## Forms

- `react-hook-form` + `zod` + `@hookform/resolvers/zod`.
- Schema lives with the form (in the component file or `model/`).
- Use `<Form>` wrapper from `shared/ui/form.tsx` for shadcn integration.
- API error → form error: surface via `setError("root", { message: extractErrorMessage(err) })`.

## Error Handling

- Inside hooks/components, catch only what you can do something with. Otherwise let React Query expose `error` and `isError` and render fallback UI.
- For HTTP errors, use `extractErrorMessage(err)` from `shared/api/client.ts`.
- For mutations, surface failures via `toast.error()`; success via `toast.success()`.

## Currency

Two units depending on the field:
- `salary` — **thousands of €** (75 = €75K).
- `marketValue`, `budget`, `balance`, transfer `fee` — **millions of €** (100 = €100M).

Use [`src/shared/lib/currency.ts`](../../src/shared/lib/currency.ts) and [`src/shared/lib/finance.ts`](../../src/shared/lib/finance.ts). The API also returns `*Formatted` strings (e.g., `balanceFormatted`) — prefer them for display when present, but the helpers exist for client-side recomputation.

## Imports

- Group order: builtins → third-party → `@/app` → `@/pages` → `@/widgets` → `@/features` → `@/entities` → `@/shared` → relative.
- Always alias to `@/`. Never reach across features (`@/features/X/internal/...`); use the feature's `index.ts`.

## Testing

### Unit / component
- Vitest config: [`vitest.config.ts`](../../vitest.config.ts). Setup in `src/test/setup.ts`.
- Test files: `*.test.ts(x)` co-located with source or in `src/test/`.
- Run all: `npm test`. Watch: `npm run test:watch`.

### E2E
- Playwright config: [`playwright.config.ts`](../../playwright.config.ts).
- Fixture: [`playwright-fixture.ts`](../../playwright-fixture.ts).
- E2E specs live in `src/tests/` (already scaffolded).

### What to test (priority order)
1. Auth flow (sign-in, session hydration, 401 → clear).
2. Save lifecycle (create, advance season, delete) — cross-domain invalidations.
3. Squad mutations (create, edit, release).
4. Transfer creation (player auto-create / link).
5. Scout filtering & shortlist add/remove.

Current coverage is light.

## Internationalisation (i18n)

All user-facing strings must go through i18next. Do not hard-code UI text.

```tsx
import { useTranslation } from "react-i18next";

const { t } = useTranslation();
<button>{t("squad.releasePlayer")}</button>
```

- Key format: `<module>.<camelCaseKey>` — e.g. `squad.releasePlayer`, `scout.filters.position`.
- Add keys to `src/i18n/locales/en.json` only; the PT-BR stub does not need updating for each change.
- Do not pass JSX or complex interpolation through `t()`. Compose translated strings with surrounding JSX instead.
- i18n is initialised in `src/i18n/config.ts` and imported in `main.tsx` before the React tree; it is available everywhere without a provider.

## Comments

- Default: **none**. Names already say what the code does.
- Add a one-line comment only when the **why** is non-obvious (a workaround, a constraint, an invariant).
- Existing comments in the codebase that explain "what" should be deleted on touch.

## Conventions to preserve

- API client section dividers (`// ─── Saves ───`).
- One React Query hook file per feature (`useX.ts`), not split per-operation.
- `import type` for type-only imports (TS isolated-modules friendly).
- Component prop interfaces declared directly above the component, not exported unless reused.
