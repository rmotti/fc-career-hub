# 3.1 Architecture

## Overview

FC Career Hub is a two-tier system: a React SPA (this repo) and a Fastify HTTP API (`docs/career-hub-api/`) backed by PostgreSQL and Redis. The frontend owns presentation, session, and cache; the API owns persistence and business rules. There is no server-side rendering and no direct database access from the client.

The frontend follows **Feature-Sliced Design (FSD)**. Each layer has a strict role and a strict import direction; this is the most important constraint to preserve.

## Frontend Layers

```
src/
├── app/         composition root (providers, router, global styles)
├── pages/       one component per route
├── widgets/     cross-feature compositions (hub-layout, auth-layout)
├── features/    domain capabilities (auth, squad, scout, ...)
├── entities/    framework-agnostic domain models (player)
└── shared/      ui (shadcn), api/client, lib, hooks, config
```

**Import direction**: `app → pages → widgets → features → entities → shared`. Lower layers must not import from higher ones.

### 1. `app/`
Composition root. Three sub-folders:
- `providers/` — wraps the tree with `QueryClientProvider`, `AuthProvider`, `TooltipProvider`, `Toaster`, and Sonner.
- `router/` — defines all routes, mounts `BrowserRouter`.
- `styles/` — placeholder (currently empty; global CSS lives in `src/index.css`).

### 2. `pages/`
Each file is a route component. Public pages (`Landing`, `Login`, `Register`, `Pricing`, `Unauthorized`, `NotFound`) live at the root of `pages/`. Authenticated pages live in `pages/hub/` and render inside `<HubLayout />`.

### 3. `widgets/`
Cross-feature compositions that don't belong to a single feature. Today: `hub-layout` (sidebar + header + outlet) and `auth-layout`.

### 4. `features/`
The domain. Each feature is a self-contained capability with internal `api/model/lib/ui` folders and a public `index.ts` barrel. Active features:

`auth`, `change-club`, `dashboard`, `field`, `history`, `new-season`, `playbooks`, `saves`, `scout`, `squad`, `stats`, `transfers`, `tutorial`.

Features should not import from sibling features directly. Cross-cutting logic gets lifted to `entities/` or `shared/lib/`.

### 5. `entities/`
Domain entities exposed as model-only modules (no UI, no providers, no React Query). Today: `player`. Holds typed projections and pure derivations consumed by multiple features.

### 6. `shared/`
Reusable code with **no** domain knowledge:
- `api/` — the HTTP layer: `http.ts` (shared core) + `modules/<domain>.ts` (typed `ApiX` types + `xxxApi` per resource) + `client.ts` (barrel re-export; the canonical import path).
- `ui/` — shadcn primitives (49 components).
- `lib/` — utilities (`utils.ts` with `cn()`, `currency.ts`, `finance.ts`, `playerPositions.ts`, `countries.ts`, `leagues.ts`, `competitions.ts`, `rounding.ts`, `playerTransferStatus.ts`).
- `config/` — runtime constants (`plans.ts`).
- `hooks/` — `use-mobile`, `use-toast`.
- `types/` — currently empty (types co-located with consumers).

## Provider Composition

[`src/app/providers/index.tsx`](../../src/app/providers/index.tsx) wraps the tree in this order (outer first):

1. `QueryClientProvider` — owns the shared `QueryClient` (created once).
2. `AuthProvider` — depends on the query client; calls `queryClient.clear()` on sign-out.
3. `TooltipProvider` — Radix provider, must wrap any `<Tooltip />` consumer.
4. `<Toaster />` and `<Sonner />` — both feedback systems available everywhere.
5. Children = `<Router />`.

Order is load-bearing: `AuthProvider` consumes `useQueryClient`, so it must be inside `QueryClientProvider`; the toasters must be inside `TooltipProvider` because some toasts render tooltips on action buttons.

## Internationalisation (i18n)

[`src/i18n/config.ts`](../../src/i18n/config.ts) initialises **i18next** with `react-i18next` before the React tree is mounted (imported in `main.tsx`, before `<App />`).

- Active locale: `en` (English), set as both `lng` and `fallbackLng`.
- PT-BR locale (`src/i18n/locales/pt-BR.json`) is a stub — partial translations, not yet surfaced in the UI.
- All translation keys live in `src/i18n/locales/en.json`.

### Usage pattern

```tsx
import { useTranslation } from "react-i18next";

const { t } = useTranslation();
// t("squad.addPlayer")
```

Key naming convention: `<module>.<camelCaseKey>` (e.g., `scout.filters.position`, `auth.loginTitle`). Add new keys to `en.json`; the PT-BR file is intentionally incomplete and does not block production.

## Routing

All routes are defined in [`src/app/router/index.tsx`](../../src/app/router/index.tsx).

### Route categories
- **Public**: `/`, `/pricing`, `/unauthorized`.
- **Public-only** (redirect to `/app` if logged in): `/login`, `/register`.
- **Protected** (require session): `/app`, and the entire hub.
- **Plan-gated** (require `PRO` or `PREMIUM`): all `/scout/*` routes.
- **Fallback**: `*` → `NotFound`.

### Guards
[`features/auth/ui/AuthGuards.tsx`](../../src/features/auth/ui/AuthGuards.tsx) exports three guards:
- `<ProtectedRoute />` — renders a loader while session hydrates, then redirects to `/unauthorized` if not authenticated.
- `<PublicOnlyRoute />` — inverse of the above; if already authed, redirects to `/app`.
- `<PlanRoute allowedPlans={[...]} />` — redirects to `/pricing` when user's plan is not in the list.

### Hub layout
All protected hub pages render inside `<HubLayout />` ([`src/widgets/hub-layout/ui/HubLayout.tsx`](../../src/widgets/hub-layout/ui/HubLayout.tsx)) which provides the sidebar (navigation, save context, plan badge) and the page header.

## Bootstrap Flow

1. `main.tsx` mounts `<App />`.
2. `<App />` renders `<Providers>` → `<Router />`.
3. `AuthProvider.hydrateSession()` runs:
   - `purgeLegacySessionToken()` removes any pre-cutover `session_token` left in localStorage (the token now lives in an httpOnly cookie).
   - Optimistically rehydrates `user` from `localStorage["session_user"]` for instant render.
   - Validates the cookie session via `authApi.getSession()` (sent with `credentials: "include"`).
   - On a `null`/error response → `clearSession()` (clears cached user, active save id, `queryClient.clear()`). `isAuthenticated` is just `!!user`.
4. `registerUnauthorizedHandler(clearSession)` is wired so any future 401 from the API triggers full sign-out.
5. Routes resolve: protected ones wait until `isLoading === false`.

## Server State Strategy

- **All HTTP** goes through the typed objects re-exported from [`src/shared/api/client.ts`](../../src/shared/api/client.ts) (defined per domain under `shared/api/modules/`): `authApi`, `savesApi`, `clubStintsApi`, `playersApi`, `fc26PlayersApi`, `teamStatsApi`, `transfersApi`, `playbooksApi`, `shortlistApi`, `savedSearchesApi`, `scoutingApi`, `chatApi`, `trophiesApi`, `clubsApi`, `competitionsApi`.
- Each feature exposes hooks (`useSaves`, `usePlayers`, `useTransfers`, ...) that wrap React Query.
- Query keys are arrays starting with the resource name: `["players", saveId, ...]`, `["saves"]`, `["saves", saveId]`, `["teamStats", saveId]`, `["trophies", saveId]`.
- Mutations invalidate the matching keys in `onSuccess`. `useUpdateSave` performs cross-domain invalidation (saves + teamStats + players + trophies) because advancing the season cascades server-side.

## API Topology

### Base URL resolution
Defined in `shared/api/http.ts` (`resolveBaseUrl`):
- Reads `VITE_API_URL` (the only supported name); accepts a relative same-origin path (`/api`, the default) or an absolute URL (cross-site escape hatch).
- When unset: same-origin `/api` in the browser; the absolute Railway host under the test runner (relative URLs can't be resolved in jsdom).
- Always appends `/api` if missing.

### Auth transport
- Calls are routed through the app's own origin (`/api`) — a Vercel rewrite in production, the Vite dev proxy locally — so the session cookie is **first-party** and survives Safari ITP. See [3.3 API and Integrations](3.3_API_and_Integrations.md#same-origin-proxy-safari-itp).
- Session token lives in a host-only, first-party **httpOnly cookie** (`Secure; SameSite=Lax`) set by the API — not readable by JS, never in localStorage.
- `request()` sends every call with `credentials: "include"`; on writes it adds a double-submit `X-CSRF-Token` header (the CSRF token is held in memory via `setCsrfToken`, lazily fetched from `GET /auth/csrf` when missing).
- 401 on non-auth paths triggers `unauthorizedHandler()` (i.e., full sign-out).
- 429 responses parse `Retry-After` for rate-limit handling.

### Error contract
Frontend `ApiError` carries `{ message, status, data, isNetworkError, retryAfter }`. The API returns one of:
- `{ error: string, statusCode: number }` (default).
- `{ error: <code>, message: <human-readable>, statusCode: number }` when `AppError.code` is set (e.g., `SHIRT_NUMBER_CONFLICT`).

`extractErrorMessage(err)` centralizes UI-facing messages. Prefer it over reading `err.data.error` directly.

## API Layer (separate repo, mirrored under `docs/career-hub-api/`)

For full reference see [`docs/career-hub-api/CLAUDE.md`](../career-hub-api/CLAUDE.md). Summary:

- **Fastify** with feature-based folders. Each feature has `routes.ts` (schema + wiring), `controller.ts` (request/response extraction), `service.ts` (business logic + Prisma).
- **Better Auth** session; the browser sends it as an httpOnly cookie, which `requireAuth()` injects as a bearer for Better Auth, resolving once per request and caching in Redis under `session:<token>` for 5 minutes. (The `Authorization: Bearer` path is kept server-side for non-browser clients like MCP/mobile.)
- **Prisma** singleton with connection pooling tuned for serverless Postgres (Neon).
- **Redis** caches list endpoints and individual resources per service-defined TTL constants; invalidation is point or `SCAN`-based pattern.
- **MCP server** plugin (`/mcp`) exposes career data as tools for the OpenAI Responses API; the Mister chat assistant uses this.

## Architectural Boundaries

### Boundary 1 — UI vs domain logic
Pages and feature UI are deliberately thin; data shape and mutation orchestration live in `model/`. Derivations (e.g., total stats, fit score breakdown) come from the API already computed.

### Boundary 2 — Global state vs screen state
- **Global**: session (`AuthProvider`), React Query cache.
- **Screen-local**: filters, dialogs, form state, selections — kept in component `useState`/`useReducer`.
- **No Context-based stores** beyond `AuthContext`.

### Boundary 3 — Frontend vs backend
- Frontend never owns business rules that affect persistence (e.g., player release rules, season cascade). It surfaces them.
- Currency unit conversion is mirrored on both sides; helpers in `shared/lib/currency.ts` match `api/src/shared/utils/currency.ts`.
